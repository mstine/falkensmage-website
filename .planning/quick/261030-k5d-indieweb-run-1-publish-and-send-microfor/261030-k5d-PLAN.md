## Decision: sent state lives in an Actions cache, bounded by a 7-day window

| Mechanism | Verdict |
|---|---|
| Commit a log back to main | Rejected. Needs `contents: write` on the job that parses untrusted HTML, and every essay leaves a bot commit Matt's checkout must pull. A `GITHUB_TOKEN` push would not actually re-trigger `push`, so the loop is avoidable, but the write scope and the churn are not. |
| State on a separate branch | Rejected. Same write scope, more git plumbing. |
| Time window alone, as in send-fa-email.py | Rejected. That script gets its dedupe from Buttondown's API. Webmention has no such query, so a window alone resends on every run inside it. |
| Diff the new build against the live feed | Rejected. Stateless and tidy, but one transient failure is lost for good, and the essay already live at first deploy would never send. |
| **Actions cache, plus MAX_AGE of 7 days** | **Chosen.** No new permissions, no commits, no deploy trigger. |

Mechanics: one tab-separated `source target` line per accepted pair in `.webmentions-sent`, appended immediately after each 2xx so a crash keeps earlier work. Key is unique per run, restore is by prefix (newest wins), save runs under `if: always()`. The workflow's existing `concurrency: pages` serializes runs, so restore, send and save cannot interleave. The nightly restore keeps the entry younger than GitHub's 7-day eviction. Only accepted pairs are recorded, so dead links and 5xx targets are retried nightly, and the window stops that at seven nights.

The failure direction is the point: a lost cache costs a duplicate inside the window, which §3.2.4 says receivers should tolerate. It can never cost a missed send, and an essay past the window can never resend.

Cache access is governed by GitHub's `cache-mode`, set by trigger type and not by `permissions:`. `push`, `schedule` and `workflow_dispatch` all default to `write` on the default branch, so leave `cache-mode` unset. One quiet edge remains: a denied save is a warning, not a failure, and its symptom would be a resend on the next run. So the sender logs how many pairs it loaded from state, which makes that visible in the job log.

**Address guard.** At the single `_opener` composition point, replace stock handlers with guarded ones, so GET, POST and every redirect hop share one chokepoint.

|----------|-------------|
| Third-party target pages to sender | HTML, Link headers, redirects and DNS are all attacker-controllable for any cited site |

| Runner to Actions cache | Sent state is read back on later runs and steers what gets sent |
| Essay markup to public parsers | Identity claims published as data, already public |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-k5d-01 | Elevation of Privilege | `fetch` and `notify`, SSRF to loopback, private ranges or cloud metadata | high | mitigate | `GuardedHTTPConnection` and `GuardedHTTPSConnection` validate the connected peer through `peer_allowed` before any request byte, covering redirects, `localhost` and DNS rebinding at one chokepoint; `::ffff:` mapped addresses unwrapped; tested over real sockets |
